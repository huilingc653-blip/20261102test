# 登录、租户隔离与 Dubbo 上下文传递方案说明

> 适用范围：bt-saas 单体多租户 SaaS 系统（Spring Cloud Gateway + Spring Security OAuth2/JWT + Dubbo + MyBatis + 共享数据库行级隔离）

> 核心代码位置：`bytter-common-base/bytter-framework`、`bytter-gateway`、`bytter-auth-parent`

## 0. 总体架构

```
浏览器/客户端
   │  Authorization / Access-Token (JWT)
   ▼
┌─────────────────────────────┐
│  Gateway (AccessGatewayFilter)│ ① 校验 JWT 签名+过期、URL 权限
│  注入 Header:               │ ② claims.getSubject()=ShiroUser JSON
│   x-client-token-user       │   claims.tenantId → X-Tenant-ID
│   X-Tenant-ID               │
└────────────┬────────────────┘
             │ HTTP (+受信任的 x-client-token-user)
             ▼
┌─────────────────────────────┐
│  Web 服务 (UserInterceptor)  │ ③ 解析 Header → ShiroUser
│  UserContextHelper(setUser) │ ④ 写入 TransmittableThreadLocal
└────────────┬────────────────┘    (userThreadLocal + tenantThreadLocal)
             │ Dubbo 调用
             ▼
┌─────────────────────────────┐
│ DubboTokenFilter(CONSUMER)  │ ⑤ 读取当前用户/租户，写入
│  setAttachment shiroUser /  │   RpcContext ClientAttachment
│  ttlTenant                  │
└────────────┬────────────────┘
             │ Dubbo RPC (attachment 随调用传递)
             ▼
┌─────────────────────────────┐
│ DubboUserProviderFilter     │ ⑥ 读取 attachment（不再写 ThreadLocal）
│ (PROVIDER, 仅清理)          │   业务代码通过 getCurrentUser()/
│                             │   getTenantId() 直接读 ServerAttachment
└────────────┬────────────────┘
             │ DB 访问
             ▼
┌─────────────────────────────┐
│ TenantDataSource            │ ⑦ 每个连接包成 TenantConnection
│  → TenantConnection         │ ⑧ interceptSQL 追加 TENANT_ID 条件
│  → TenantSQLHandler         │   (jsqlparser 改写 SQL)
└─────────────────────────────┘
```

核心设计思想：**用户/租户身份在网关一次性鉴别，之后以 "受信任 Header + Dubbo Attachment" 向下游透传；业务侧通过 `UserContextHelper` 统一获取；数据库访问层用 SQL 改写强制追加 `TENANT_ID` 过滤条件，实现行级租户隔离。**

## 1. 登录与认证方案

### 1.1 令牌签发（bytter-auth）
- 基于 **Spring Security OAuth2**（`AuthorizationServerConfig`）签发 JWT 访问令牌。
- 令牌 `subject` 写入 `ShiroUser` 的 JSON 序列化串，`tenantId` 作为 claim 写入（见 `ApiAuthenticationServiceImpl`、`LoginTokenController`）。
- 服务端通过 `TokenStore` 管理令牌，支持吊销（`consumerTokenServices.revokeToken`）。

### 1.2 网关统一鉴权（bytter-gateway `AccessGatewayFilter`）
关键逻辑（`AccessGatewayFilter.java:67-123`）：
1. 从 Cookie/Header(`Authorization`)/参数(`access_token`) 取出 token；
2. `authService.checkToken(token)`：走 OAuth2 `TokenStore` 校验存在性与过期；
3. `authService.getJwt(token).getBody()`：解析 JWT claims，校验过期；
4. `authService.hasPermissionV1(uid, url, method, tenantId)`：URL 级权限校验（基于 Redis 缓存的 url→权限码映射）；
5. **注入受信任请求头**：
   - `x-client-token-user` = `URLUtil.encode(claims.getSubject())`（即 ShiroUser JSON）；
   - `X-Tenant-ID` = `claims.get("tenantId")`。

> ⚠️ 注意：网关是唯一的"信任边界"。服务内部**不再验签**，直接信任 `x-client-token-user` 头。

### 1.3 Web 层用户上下文装配（bytter-framework `UserInterceptor`）
- 通过 `BytterWebMvcConfig` 注册为全局拦截器，`excludePathPatterns` 排除 `/login`、`/oauth/**`、`/oauth2/**`、`/userLoginType`、`/swagger-ui.html`、`/static/**`（`BytterWebMvcConfig.java:13`）。
- 从 `x-client-token-user` 取出并 `URLDecoder.decode` 后 `JSON.parseObject(..., ShiroUser.class)`，再调用 `UserContextHelper.helper().setUser(shiroUser)` 写入 `TransmittableThreadLocal`（`UserInterceptor.java`）。

## 2. 租户隔离方案

### 2.1 隔离模型：共享库 + 行级 `TENANT_ID`
- 所有租户共用同一数据库/表，每张业务表带 `TENANT_ID` 列。
- 在 JDBC 连接层对**每一次 SQL** 强制改写，追加 `TENANT_ID = ?` 过滤条件（而非依赖业务代码手写 where）。

### 2.2 数据源包装（`TenantDataSource` → `TenantConnection`）
- `TenantDataSource` 包装真实数据源，每次 `getConnection()` 返回 `TenantConnection`（`TenantConnection.java:21`）。
- `TenantConnection` 实现 `java.sql.Connection`，对所有 `prepareStatement/prepareCall/createStatement` 做拦截。

### 2.3 SQL 改写（`TenantSQLHandler` + jsqlparser）
- 使用 **jsqlparser** 解析 SQL AST，对 `FROM/JOIN` 的每个表、以及 `SubSelect` 子查询递归追加 `TENANT_ID` 条件；对 `INSERT` 注入 `TENANT_ID` 列值。
- 通过 `TenantProperties` 配置：
  - `columnName`（租户字段名，默认TENANT_ID）；
  - `tenantId`（全局租户默认ID）
  - `excludeTables`（排除租户改造的表）；
  - `specialTables`（特殊表，添加全局租户条件，tenant_id in ('xxxx','全局租户ID')）；
  - `excludeTablePrefix`（排除表前缀列表，用于匹配大量同前缀的表，比如工作流表）
  - `dbType`（数据库类型：MYSQL / ORACLE，默认 MYSQL，用来给关键字追加分割符）
  - `enabled`（总开关，true/false：启用/关闭，用于适配单租户---开发中）。

### 2.4 租户 ID 解析链（`UserContextHelper.getTenantId()`）
```
tenantThreadLocal.get()                         // ① Web 线程内已 set
  → getAttachmentFromDubbo("ttlTenant")         // ② Dubbo ServerAttachment
  → getCurrentUser().getTenantId()              // ③ 回退到 ShiroUser.tenantId
```
- `getCurrentUser()` 解析链：先取 `userThreadLocal`，为空再读 Dubbo `shiroUser` 附件并反序列化（`UserContextHelper.java`）。
- `TenantConnection.getTenantId()` 直接调用 `UserContextHelper.helper().getTenantId()`，从而把"线程/调用上下文中的租户"落到每一条 SQL。

### 2.5 历史方案（已废弃/注释）
- `TenantContext` + `TenantInterceptor`（基于 MyBatis 插件 + 独立 `ThreadLocal`）整文件已注释，已被 `UserContextHelper` 方案取代。

## 3. 用户/租户上下文传递方案

统一载体是 `UserContextHelper`（`com.bytter.core.common.context`），内部两个 `TransmittableThreadLocal`（阿里 TTL，解决线程池复用导致的上下文丢失）：
- `threadLocal`：`ShiroUser`（用户身份）；
- `tenantThreadLocal`：`TENANT_ID`（租户）。

### 3.1 Web → Dubbo 消费者（`DubboTokenFilter`，`@Activate(CONSUMER), order=1`）
- 读取 `UserContextHelper.helper().getCurrentUser()` 与 `getTTLTenant()`；
- 写入 Dubbo `RpcContext.getClientAttachment()`：
  - 有用户 → `setAttachment("shiroUser", JSON)`；
  - 仅租户 → `setAttachment("ttlTenant", tenantId)`；
- `finally` 中 `clearAttachments()` 清理，避免污染下一次调用（`DubboTokenFilter.java`）。

### 3.2 Dubbo 提供者（`DubboUserProviderFilter`，`@Activate(PROVIDER), order=1`）
- **当前生效逻辑**（第 18-35 行）：仅读取 `shiroUser`/`ttlTenant` 附件，在 `finally` 中 `RpcContext.removeContext()` 清理，**不再把上下文写入 ThreadLocal**。
- 业务代码在 Provider 侧获取用户/租户，是通过 `getCurrentUser()/getTenantId()` **直接读 `RpcContext.getServerAttachment()`（第 2.4 节兜底②/③）**完成的。
- 注释掉的大段代码（第 37-92 行）是原方案：在 Provider 把附件 `setUser` 进 ThreadLocal，并在 `finally` 恢复原始上下文。注释说明原因为**"线程池污染"**（`getCurrentUser()` 在 TTL 为空时会回退读 ServerAttachment，导致把本次传入的 shiroUser 误当原始用户，跨请求残留）。

> 设计取舍：Provider 端放弃注入 ThreadLocal，改为"读取时即时从 Dubbo 附件取"，规避了 ThreadLocal 在线程池中跨请求污染，但代价是**异步/新线程内上下文丢失**（见 §5）。

### 3.3 异步 / 线程池
- `SmartThreadPoolManager` 与 `TenantShardingExecutor`：提交任务前捕获当前 `TENANT_ID`，在任务执行体内 `setTTLTenant(tenantId)` + `finally clearTTLTenant()`（仅透传**租户**，不透传完整用户）。
- 前提是使用这些受管线程池；若直接用 `new Thread()`/`CompletableFuture` 默认线程池而未包装，TTL 不会自动继承，租户与用户同时丢失。

### 3.4 消息队列 / 流式（MQ / Spring Cloud Stream）
- **生产者**（`TenantAwareStreamBridge.send`）：自动在消息头写入 `X-Tenant-Id`（`MessageHeaders`），保证消息携带租户。
- **消费者**：**全局拦截器 `TenantAwareFunctionInterceptor` / `TenantAwareFunctionCatalogConfig` 已整段注释（无法随应用启动）**。目前由各业务 listener **手动**从 `X-Tenant-Id` 头取出并 `setTTLTenant`，`finally` 中 `clearTTLTenant`（如 `RecordBookingEvent`、`InitNetDayCloseEvent`、`FinacialToPaymentEvent` 等）。
- 同样只透传租户，不还原用户身份。

## 4. 方案优缺点

### 优点
1. **统一入口、集中鉴权**：认证与 URL 权限集中在网关，下游服务无感知，便于统一管控与横向扩展。
2. **强制行级隔离**：在 JDBC 连接层改写 SQL，业务代码无需（也几乎无法）手动拼接 `TENANT_ID`，降低"漏写 where"导致的越权风险。
3. **上下文获取 API 统一**：`UserContextHelper.getCurrentUser()/getTenantId()` 一套接口贯穿 Web、Dubbo、DB，使用简单。
4. **跨进程透传开箱即用**：Dubbo Filter + Attachment 自动把用户/租户带到 Provider，无需业务显式传参。
5. **使用 TTL 兼顾线程池**：相比原生 `ThreadLocal`，采用 `TransmittableThreadLocal` 可缓解线程池复用下的上下文丢失。
6. **支持超级租户/表白名单**：`TenantProperties` 可灵活放开公共表与超级管理员，适配多租户下的非隔离场景。

### 缺点
1. **DB 层"软隔离"而非"硬隔离"**：共享库共享表，一旦上下文丢失（见 §5），隔离立即失效，且无第二道防线。
2. **Provider 端上下文"按需读取"而非"显式注入"**：业务代码依赖 `getCurrentUser()` 的 Dubbo 附件兜底，开发者不易察觉异步/新线程下会失效。
3. **上下文透传不彻底**：异步与 MQ 只透传租户、不透传用户，导致异步链路中"操作人/审计字段"普遍缺失。
4. **MQ 租户还原依赖人工**：无全局消费者拦截器，每个 listener 需手动 `setTTLTenant`，易遗漏。
5. **网关信任头缺乏二次校验**：下游完全信任 `x-client-token-user`，一旦绕过网关即可伪造。
6. **SQL 改写有语法边界**：依赖 jsqlparser，对复杂/非标准 SQL（存储过程、特殊方言、动态拼接、批量/多语句等）可能无法改写或改写不正确。

## 5. 潜在问题与风险（重点）

### 🔴 风险 1：JWT 签名密钥硬编码，可伪造令牌（高危）
`AuthServiceImpl.getJwt()`（`bytter-gateway/.../auth/service/impl/AuthServiceImpl.java:84-87`）：

```java
return Jwts.parser()
        .setSigningKey("ByTtEr".getBytes(StandardCharsets.UTF_8))   // 硬编码
        .parseClaimsJws(jwtToken);
```
- 代码中已注入 `${spring.security.oauth2.jwt.signingKey}` 字段（`signingKey`）却**未使用**，实际签名/验签使用硬编码字符串 `"ByTtEr"`；`getJwt2` 同样硬编码。
- 任何能接触到源码或猜出密钥的人，都能**自行签发任意 `subject`（任意 ShiroUser）与 `tenantId` 的 JWT**，网关验签通过，下游直接信任。
- 后果：可伪造任意用户、任意租户身份，**直接横向越权访问其他租户数据**；同时令"网关信任头"形同虚设。
- 建议：密钥必须来自配置中心/环境变量，且各服务共享一致；禁止硬编码；考虑非对称密钥（RS256）让网关仅持公钥验签、auth 持私钥签发。

### 🔴 风险 2：`tenantId == null` 时 SQL 完全不加租户过滤（高危）
`TenantConnection.prepareStatement/prepareCall`（`TenantConnection.java:41-53` 等）：

```java
String tenantId = getTenantId();
if (tenantId != null) {
    ParsedSQL parsed = interceptor.interceptSQL(sql, tenantId);
    ... delegate.prepareStatement(parsed.getSql());
}
return delegate.prepareStatement(sql);   // ← tenantId 为 null 时直接放行，无任何过滤
```
- `getTenantId()` 在"无用户 ThreadLocal、无 Dubbo `ttlTenant` 附件、无 `shiroUser`"时返回 `null`。
- 触发场景：① 定时任务/内部调用未设置租户；② 异步线程（未走受管线程池）；③ MQ 消费者遗漏 `setTTLTenant`；④ Provider 异步派生线程。
- 后果：该 SQL 跨租户查询/写入**全部租户数据**，属于静默数据泄露/污染，且很难在测试期发现。

### 🟠 风险 3：下游服务盲目信任 `x-client-token-user`（中高危）
- `UserInterceptor` 直接 `JSON.parseObject(header, ShiroUser.class)`，不做签名校验。
- 若任何服务可直连（内网暴露、链路未强制过网关、容器网络可达），攻击者可自行构造该 Header 冒充任意用户/租户。
- 建议：服务间调用也应由网关或 mTLS + 内部 token 校验；或在服务侧对来自 Header 的用户信息做轻量校验/来源白名单。

### 🟠 风险 4：Provider 异步/新线程上下文丢失，且只透传租户
- Provider 端未注入 ThreadLocal（§3.2）。在 Provider 业务里若 `CompletableFuture`、MQ 发送、 `@Async` 等切换到新线程：
  - `getCurrentUser()` 读不到 ServerAttachment → 返回 `null`；
  - `getTenantId()` 因 `tenantThreadLocal` 为空且附件不可继承 → 也返回 `null` → 触发风险 2。
- 即使使用 `SmartThreadPoolManager`/`TenantShardingExecutor`，**只 setTTLTenant（租户），用户身份仍丢失**，导致 `createBy/updateBy` 等审计字段为空或错误。

### 🟠 风险 5：MQ 租户还原靠人工、且无统一拦截器
- `TenantAwareFunctionInterceptor`、`TenantAwareFunctionCatalogConfig` 已注释（注释称"无法随应用启动"）。
- 现有每个 listener 需手动 `setTTLTenant`，**新增 listener 极易遗漏** → 触发风险 2。
- 同时只还原租户，不还原用户，异步消费侧无操作人信息。

### 🟡 风险 6：`getTTLTenant()` 与 `getTenantId()` 语义不一致
- `getTTLTenant()` 只取 `tenantThreadLocal`；`getTenantId()` 额外回退到 Dubbo 附件与 ShiroUser。
- Provider 端 `tenantThreadLocal` 为空，`getTTLTenant()` 返回 `null` 而 `getTenantId()` 正常返回。若业务代码混用二者，会在 Provider 侧出现"租户取不到"的诡异现象。

### 🟡 风险 7：SQL 改写的边界与正确性
- jsqlparser 对以下场景可能改写失败或遗漏：`UNION`、多语句、`INSERT ... SELECT`、存储过程/函数、数据库方言专有写法、MyBatis 动态 SQL 拼接出的非常规语句。
- `TenantProperties.exclusions` 维护遗漏（新增公共表未登记）也会造成误加/漏加过滤。
- 建议在 CI/测试环境对核心 SQL 开启改写日志（项目中已有 `logSql`/`logRsSql` 开关）做回归校验。

### 🟡 风险 8：`RpcContext.removeContext()` 在 Provider finally 中的副作用
- `DubboUserProviderFilter.finally` 对两种附件分别调用 `RpcContext.removeContext()`。虽在调用结束后清理，但 `removeContext()` 清除的是**整个** RpcContext，若过滤器链后续还有依赖 ServerAttachment 的逻辑会被清空；且逻辑略显"防御性过度"。建议仅 `clearAttachments()`。

### 🟡 风险 9：网关 `X-Tenant-ID` 与 `subject` 中 tenantId 冗余且不一致处理
- 网关同时下发 `X-Tenant-ID` 与 `x-client-token-user`（内含 tenantId），但 Web 层只认后者；若二者被分别篡改会出现不一致。统一以 ShiroUser.tenantId 为准是对的，但建议删除冗余头、避免歧义。

## 6. 改进建议（按优先级）

1. **【紧急】消除硬编码 JWT 密钥**：启用 `${spring.security.oauth2.jwt.signingKey}`，移除 `"ByTtEr"` 硬编码；优先采用 RS256（auth 私钥签发、网关/服务公钥验签）。
2. **【紧急】为 null 租户加"兜底策略"**：在 `TenantConnection` 中，当 `tenantId == null` 时**拒绝执行**或抛出明确异常（而非静默放行）；对确需跨租户的后台任务显式标注白名单。
3. **【高】补全 MQ/异步的上下文透传**：实现可用的全局消费者拦截器（参考被注释的 `TenantAwareFunctionInterceptor`），统一从消息头还原租户；并扩展为同时透传用户（用 TTL 装饰 Runnable/Callable）。
4. **【高】服务侧对受信任头做校验或来源约束**：确保服务仅在经由网关/mTLS 的内部网络可达；必要时对 `x-client-token-user` 做轻量签名校验或来源 IP/Header 白名单。
5. **【中】统一语义**：将 `getTTLTenant()` 与 `getTenantId()` 收敛为同一解析链，避免 Provider 侧行为差异。
6. **【中】推行受管线程池**：全项目统一使用 `SmartThreadPoolManager`/`TenantShardingExecutor` 或 TTL 包装器，禁止裸 `new Thread()`/`CompletableFuture` 默认池。
7. **【中】SQL 改写回归测试**：在测试/预发环境开启改写日志，对核心报表/批量 SQL 做租户条件断言。
8. **【低】移除冗余 Header 与防御性 `removeContext`**，改为精确 `clearAttachments()`。
